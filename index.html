02

Your Mac's chip and memory

On Apple Silicon the processor and graphics share one pool of memory, so these two answers decide almost everything.

Chip
Where do I find this?
  1. Click the apple menu in the top-left corner.
  2. Choose About This Mac.
  3. Read the line labelled Chip — for example "Apple M2 Pro".

If that line says "Processor" and mentions Intel Core, choose Intel.

Max chips only: Max models come in two versions with different memory speeds, up to 33% apart, so the GPU core count matters. In the same window click More Info → System Report → Graphics/Displays to see the core count. If you can't find it, pick the lower one — it's the more common configuration and keeps the estimate conservative.

Memory
Where do I find this?
  1. Click the apple menu → About This Mac.
  2. Read the line labelled Memory.

Same window as the chip, so you can read both at once.

02

Your memory and graphics card

A graphics card with its own memory makes models run several times faster. Plenty of laptops don't have one — smaller models still work well without.

Installed RAM
Where do I find this?
  1. Press Windows + I to open Settings.
  2. Go to System → About.
  3. Under "Device specifications", read Installed RAM.

It may say "16.0 GB (15.8 GB usable)" — choose the first number.

  1. Open your Settings app.
  2. Go to About or System Details.
  3. Read the Memory line.

Prefer a terminal? free -h reports the same thing and changes nothing.

Which one?
How do I tell the exact model?
  1. The full name appears in Device Manager → Display adapters.
  2. To confirm the memory: Ctrl + Shift + Esc, click More details if needed, then Performance → your GPU → Dedicated GPU memory.

Only see "Shared GPU memory"? That's built-in graphics — go back and choose Built-in only. And note a laptop card is not the same as the desktop card of the same name: a laptop RTX 4090 has 16 GB and roughly half the memory speed of the desktop version.

  1. lspci | grep -i vga gives the model name.
  2. nvidia-smi reports the memory. Both only read.
Roughly how old is the laptop?
Why does this matter?

It stands in for memory generation. When any part of a model runs on the processor, system memory speed sets the pace, and DDR5 is roughly 60% faster than DDR4. A rough answer is enough.

What will you use it for?

Both answers change the result. Longer inputs need substantially more memory, which is the part most fit calculators leave out.

Main use
How much text at once?
How do I choose?

Roughly 750 words is 1,000 tokens. Back-and-forth chat rarely passes 4k. Pasting a long report or several source files is 32k territory. The memory a model needs for this grows with the length and can exceed the size of the model itself — which is why a model that "fits" for chat can fail outright on long documents.

How to actually run one

  1. Install LM Studio for a normal app window, or Ollama if you're comfortable in a terminal. Both are free.
  2. Search the model name and download the Q4_K_M build — that's what these estimates assume. Below about 4B parameters, prefer Q5_K_M or Q6_K; small models lose noticeably more quality to aggressive quantisation.
  3. Set the context length in the app to match what you chose here. Leaving it at the model's maximum will reserve far more memory than you need.
  4. If generation is slower than estimated, close your browser first. It's usually the browser.

Methodology

How these numbers are produced

This is a planning aid with stated error bars, not a benchmark. Everything below is arithmetic you can check, and where a figure is a judgement call rather than a measurement it is labelled as one.

In plain terms

If none of this is familiar, read this part first. It explains the whole model in ordinary language, and every formula further down is one of these ideas written in symbols.

A

Why does a model need so much memory?

Picture an enormous reference book. To produce one single word, the model has to consult every page of it — not skim, not look things up in an index, but read the whole thing start to finish. Then to produce the next word, it reads the whole book again.

Memory is the desk that book has to lie open on. If the book doesn't fit on the desk, you can't work at all.

That's why fit is a hard yes or no rather than a gradual slowdown, and why a model's file size is the number that matters most. The "book" is the model's weights — the billions of numbers it learned during training.

B

What's actually taking up the space?

Three things share the desk:

The book — the model's weights. Fixed size. This is what you download.

The notepad — as the conversation goes on, the model keeps notes on everything said so far so it doesn't have to re-derive it every time. The notepad grows as the conversation grows.

Elbow room — space to actually work in. Small and roughly fixed.

The notepad is the part most fit calculators ignore, and it's why this page asks how much text you'll use at once. Paste in a whole codebase and the notepad can end up needing more space than the book. A model that fits comfortably for short chat can fail outright on long documents — same model, same laptop, different job. The notepad is what's called the KV cache.

C

Why is one model faster than another?

Since every word means reading the whole book, speed comes down to how fast you can turn pages. A book twice as thick takes twice as long per word. A reader who turns pages twice as fast finishes in half the time.

That's the entire speed calculation: pages divided by page-turning rate.

The surprising consequence is that a faster processor barely helps. The machine isn't thinking slowly, it's reading slowly — so what matters is how fast your computer can pull data out of memory. That rate is called memory bandwidth, and it's why this page asks about your chip and the age of your laptop. It's also why an old laptop with lots of RAM can hold a big model and still be painful to use: a big desk doesn't make you a faster reader.

D

What happens when it almost fits?

On a Windows or Linux laptop with a graphics card there are two places to put the book: the desk right in front of you, which is the card's own memory, and a shelf across the room, which is ordinary system RAM.

Pages on the desk are read almost instantly. Pages on the shelf mean standing up and walking over. When the book doesn't fit on the desk, you don't give up — you keep as much as fits on the desk and leave the rest on the shelf.

This is the situation most laptops are actually in, and it's why a model can be split across both. But notice the shape of it: leaving even a quarter of the book on the shelf means most of your time goes to walking. A model that's 80% on the graphics card doesn't run at 80% speed — it runs far closer to the slow tier than the fast one. That's why the report shows the split as two coloured segments rather than a single "it fits" tick.

E

Why do some very large models run quickly?

Some newer models aren't one enormous book but a set of specialist volumes — an encyclopedia. For each word, a router decides which two or three volumes are relevant and reads only those.

You still need shelf space for the entire encyclopedia. But you only read a small part of it per word.

So these models need memory like a huge model and generate at the speed of a small one. Qwen3 30B-A3B in the list is one: 30 billion parameters of storage, about 3 billion read per word. Any calculator that treats it as an ordinary model gets it wrong twice over — too pessimistic on speed, and misleading on memory if it reasons backwards from speed. These are called mixture-of-experts models.

F

Why a range instead of one number?

You can work out a drive by dividing distance by the speed limit. The answer is real and useful, and it will still be wrong, because of traffic, lights, weather and how heavy your foot is.

Same here. The arithmetic gives a defensible central figure; the actual result moves with which program you run it in, how hot your laptop is, and what else is open. A range is the honest form of the answer. Treat the midpoint as the least interesting part of it.

G

Why is there a pause before it starts answering?

Two different jobs happen. First the model reads your question — and it can take that in many pages at once, all in parallel. Then it writes its answer, strictly one word at a time, reading the whole book for each one.

Reading is limited by raw calculating power; writing is limited by page-turning speed. They're different bottlenecks with different fixes. The estimates on this page only cover the writing. If you paste in a long document, the pause before the first word can be the largest part of the wait, and nothing here predicts it.

The same thing, in symbols

Memory available

↑ the desk, from section A

Apple Silicon shares one memory pool between processor and graphics, so the budget is a fraction of total RAM. Windows and Linux machines get two separate budgets — graphics memory and system memory — because a model can be split across both.

Apple Silicon budget = RAM × 0.70 Intel Mac budget = RAM − max(3.5, RAM × 0.18) Windows/Linux VRAM budget = VRAM − 0.8 (display and compositor) RAM budget = RAM − max(3.5, RAM × 0.18)

What a model actually needs

↑ book + notepad + elbow room, from section B

Weights are the file on disk. The KV cache holds the attention state for everything in the context window and grows linearly with it — at long contexts it can exceed the weights. Runtime overhead covers the compute buffers and the process itself.

need = weights + (kv_per_1k × context_k) + overhead

Speed, and why a model can be split

↑ page-turning rate and the shelf across the room, from sections C, D and E

Generating one token requires reading every active parameter from memory once, so single-stream decoding is bound by memory bandwidth rather than compute. llama.cpp offloads whole layers to the GPU and runs the rest on the CPU, which makes the transition between the two continuous rather than a cliff — the common case on a laptop with 8 GB of VRAM is that most of a mid-sized model sits on the GPU and the remainder does not.

f = fraction of weights resident in VRAM W = bandwidth-relevant weight bytes (active params for MoE) sec/token = (f × W) / (BW_gpu × E_gpu × M_gpu) + ((1 − f) × W) / (BW_cpu × 0.55 × M_cpu) E_gpu = 0.80 discrete NVIDIA / AMD E_gpu = 0.68 Apple unified memory M_gpu = 0.35 MoE, 1.00 dense M_cpu = 1.12 MoE, 1.00 dense

These constants are the fraction of theoretical peak bandwidth an inference runtime actually reaches. They are not guesses: each was derived from a measured throughput figure and cross-checked against others. Apple unified memory lands lower than a discrete card, and CPU lower still, because CPU inference is partly compute-bound and rarely saturates the bus.

Mixture-of-experts models need a separate constant on each side of the split, and the two point in opposite directions. Resident on a GPU they run well below the bandwidth ceiling: only a few billion parameters are read per token, which is too little work to saturate the bus, so scattered expert gathers and per-layer launch overhead dominate instead — a 3B-active model on an M4 Max generates around 70 tokens per second where raw bandwidth would allow roughly 300. Offloaded to the CPU they run above what a uniform split predicts, because llama.cpp moves expert layers specifically and keeps attention on the card. Using one number for both was the largest error in earlier versions of this page: 1.10 was fitted on two partial-offload measurements in which the GPU term contributes about 5% of total time, left the resident path effectively unconstrained, and overstated fully-resident MoE throughput by roughly three times.

The reported range is ±30% around the central figure — roughly the spread introduced by runtime version, quantisation variant, thermal state and background load. Prefer the range to the midpoint.

MoE models are handled separately in both directions: memory follows the total parameter count, speed follows the active count. Treating them as dense produces answers that are wrong twice.

One consequence worth stating plainly: the 10–16 GB size band is thin in the current generation, because the major families have polarised toward small models and mid-size ones around 17 GB. If nothing in that range suits you, a mixture-of-experts model split across your card and system memory is usually the better answer than a smaller dense one — only a few billion parameters are read per token, so the slow half of the split costs far less than it would for a dense model of the same size.

These constants were chosen by fitting against a handful of commonly reported figures — an 8B at Q4 on a laptop GPU, a 32B on Apple Silicon, an 8B on DDR5 with no GPU. That is calibration against anecdote, not measurement, which is exactly why the validation section below matters.

Fine-tuning

↑ a second engine, not an extension of the first

Training shares none of the arithmetic above. It cannot use the Q4_K_M file at all — that is an inference format — so it works from parameter count rather than size on disk, and the memory it needs is made of different parts: weights at training precision, gradients, optimiser state, and activations in place of a KV cache.

full FT = p × 16 bytes bf16 weights 2 + bf16 grads 2 + fp32 Adam m,v 8 + fp32 master 4 LoRA = p × 2 bytes + adapter + activations base frozen, no grads or optimiser state for it QLoRA = p × 0.55 + adapter + activations NF4 4-bit plus quantisation constants adapter = p × 0.004 × 12 bytes rank-32 on attention projections activations ≈ 0.05p + 0.5 GB seq 2048, batch 1, gradient checkpointing disk = p × 2 GB bf16 weights, for BOTH paths

Three consequences are worth stating outright. Full fine-tuning is not possible on a laptop for any model here — even a 1.7B needs about 27 GB, and a 12B needs nearer 190 GB. The disk figure is the one that surprises people: a 4-bit run still downloads the bf16 weights first, so fine-tuning the 27B needs 54 GB of free space even though it only occupies 19 GB of graphics memory. And a mixture-of-experts model gives nothing back here — every expert must be resident and updated, so memory follows the total parameter count, not the active one.

Unlike inference, training does not split across graphics and system memory: there is no laptop-viable equivalent of layer offload, so the budget is the fast tier alone. That makes the verdict much more binary, and much more dependent on which machine you are on. QLoRA as commonly meant is CUDA-only — bitsandbytes has no Metal backend — so on Apple Silicon the 4-bit path is MLX's own implementation, named separately here because it is a different stack. Intel Macs, AMD laptops and machines without a dedicated card get no local path at all, and are told so rather than given a number.

These figures are calculated, not measured. The bytes-per-parameter constants are standard and checkable; the activation heuristic and the fit thresholds are not calibrated against anything, and there are no validation anchors for them of the kind the speed estimates have. They are shown in a quieter visual register for that reason, and should be read as an order of magnitude rather than a specification.

What this does not model

  • Prompt processing Estimates cover generation only. Reading your prompt in is compute-bound, not bandwidth-bound, and follows completely different rules. For long documents and retrieval workloads it often dominates total time — a machine that generates at a comfortable rate can still take a long pause before the first word.
  • Thermal throttling These are burst figures. Sustained generation on a thin or fanless laptop settles meaningfully lower once the chassis warms up.
  • Quantisation quality Q4_K_M is a quality tradeoff, not only a size one, and it costs small models disproportionately more than large ones. A 3B model at Q4 is degraded in ways a 32B at Q4 is not.
  • Layer granularity Offload is modelled as a continuous fraction. Real runtimes move whole layers, so actual splits land on discrete steps near the estimate.
  • Training time The fine-tuning block answers whether a run fits, never how long it takes. On a laptop, expect a LoRA run over a few thousand examples to take hours rather than minutes, and scale from there. Fitting and finishing are different questions.
  • Speculative decoding, batching and multi-GPU All unmodelled. Each can move throughput substantially away from these figures.

Which anchor sets which constant matters. The first row pins the Apple unified-memory constant, and it only implies 0.68 on the 32-core M4 Max at 410 GB/s — on the 40-core part at 546 GB/s the same measurement would imply 0.51. Since this page splits Max chips into two bindings precisely because the gap is that large, the binding is now stated rather than left to the reader.

The MoE rows no longer agree with each other, and that is the honest result. An earlier version used a single constant of 1.10 for mixture-of-experts models, derived from the two offload rows, and reported them as agreeing on 1.12. They do agree — but only because the GPU term contributes roughly 5% of total time in both, which leaves the resident path essentially unmeasured. Carried over to a model sitting entirely in fast memory, that constant predicted a 3B-active MoE on an M4 Max at over 200 tokens per second against a reported 70.

Splitting it in two fixes the resident case (row 6, within 3%) and keeps the heavy-offload case (row 8, within 3%), at the cost of under-predicting the 3090 by 22%. That residual is real and worth naming: at 78% resident, llama.cpp's expert-specific offload is furthest ahead of the uniform split this page assumes, and no single pair of constants captures both ends. It sits inside the stated ±30% band, and errs slow.

Eight anchors now cover both memory architectures, dense and MoE, and full, partial and heavy offload. Still missing: anything on AMD, anything at long context where the cache dominates, any sustained rather than burst measurement, and a controlled measurement for the fully-resident MoE row, which is currently a reported figure rather than a first-hand one. Results — with machine specification, runtime version, model build and context length — are welcome as issues on the repository.
